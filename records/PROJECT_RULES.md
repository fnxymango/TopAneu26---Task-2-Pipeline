## 0. 구조 변경은 제출본 기준으로 적는다 — 2026-09-10 사용자 지시

**기준선이 두 개다. 섞지 않는다.**

| | 기준선 | 성격 |
|---|---|---|
| **성능 비교** | 그 시점의 **최고 모델** | 움직인다. 고도화로 더 좋은 게 나오면 그걸 기준으로 비교해도 된다 |
| **구조 변경 명세** | 언제나 **현재 제출본** (`~/SUBMISSION/`) | 고정이다. 절대 옮기지 않는다 |

즉 "A 대비 +0.02" 같은 비교는 최신 최고 모델을 상대로 해도 되지만, 제출본에서부터
구조가 달라진 부분이 있으면 **그 누적 차이 전부**를 아래 형식으로 적어야 한다.
변경 2개가 쌓였으면 "제출본 → 1 → 2" 를 전부 적는다. "1 → 2" 만 적지 않는다.
그래야 어느 시점에 실제로 제출하려 할 때 그 문서 하나만 보고 반영할 수 있다.

(2026-09-10 기준 제출본 = 팀 통합본. 우리 E9 는 여기 안 들어가 있고 `~/e9_bundle_experiment/` 에 있다.)

실험 결과가 나오면 지표만 적고 끝내지 않는다. **"제출본의 어느 파일 어느 부분을 어떻게
고치면 되는가"** 로 환산해 `~/SUBMISSION/APPLY_CHANGES.md` 에 적는다. 항목마다 반드시:

1. **성격** — 이미지 변경인가 모델 tar 변경인가 (모델 tar 만이면 재빌드가 필요 없다)
2. **파일 경로** — 컨테이너 안 절대경로. 줄 번호나 앵커 문자열까지
3. **바꿀 내용** — 그대로 복붙 가능한 형태
4. **함정** — 조용히 무효가 되는 조건 (예: `pipeline_case.py` 는 케이스 id 를 `"case"` 상수로
   쓰므로 케이스별 표를 조회하는 피처는 컨테이너에서 아무 일도 안 한다)
5. **검증** — 반영이 실제로 먹었는지 확인하는 방법 (로그 문자열·산출 대조)
6. **런타임 영향** — GC 한도 420초 기준

실험 폴더(`experiments/<실험명>/NOTES.md`)에는 **무엇을 바꿨고 무엇은 그대로인지**를
표로 남긴다. 재사용한 산출물, 외부에서 가져온 파일은 md5 를 함께 적는다.

> 이유: 제출본과 우리 최고 모델이 갈라진 뒤로 "어느 쪽 숫자인가" 를 매번 다시 확인해야 했다.
> 성능 비교는 최고 모델을 쫓아가야 진보를 재는 의미가 있지만, **적용 명세까지 같이 움직이면
> 제출 시점에 무엇을 어떻게 바꿔야 하는지 아무도 재구성할 수 없게 된다.** 그래서 명세 기준선만
> 제출본에 못박는다. 개선이 여러 겹 쌓여도 문서 하나로 제출본 → 현재를 재현할 수 있어야 한다.

### 분류기 실험 채택 판정 = K0 병변 짝지은 장치 — 2026-09-15 사용자 승인

기준선 시드만 바꿔도 val MCC 가 0.608~0.699 로 흔들려 "test·val 각각 ΔMCC ≥ −0.005" 는 병변 몇 개짜리 개선을 못 가른다.
분류기 실험은 `experiments/D1_newdata/k0_judge.py <기준태그> <후보태그>` 로 판정한다(규칙은 스크립트 머리말).

- 영가설 보정 통과(기준선 10시드 5·5 분할 504 비교 거짓 양성 0.000 · `RESULTS_K0_NULL.md`).
- 탈락한 스크리닝 후보를 올리거나 여러 후보를 한꺼번에 올리면 결과 보기 전에 α 를 낮춘다(`K0_ALPHA`).
- 7지표 test·val 은 보조로 함께 적는다. 채택 권고가 나와도 실제 기준선 교체·제출 반영은 사용자 결정.

### gC(topk 2등 조각) — **ON 으로 확정** (2026-09-11, 7지표 판정 후)

```

```
**더 이상 축으로 삼지 않는다.** 다시 건드릴 필요가 생기면 사용자에게 먼저 묻는다.

판정 근거 — 동결 eval 660da7a **7지표**(F1 포함), 개정판 학습표 위 gC OFF − ON:
```
test  개선 5/7 충족    (F1 −0.0057)
val   개선 4/7 미충족  (F1 −0.0226 · RECALL −0.0364 · HD95 +5.09)
```
6지표일 때는 test·val 둘 다 충족이었으나 **F1 이 들어오며 val 이 뒤집혔다.**

- **분류기를 세부 변경할 때마다 gC on/off 를 같이 재지 않는다.** 실험 축이 두 배가 되고
  상호작용에 결론이 흔들린다(실측: gC OFF 는 구 학습표에서 ±0.001 무효, 개정판 학습표에서

- gC 를 다시 건드릴 필요가 생기면 **사용자에게 먼저 묻는다.** 임의로 재지 않는다.


## 1. 공식 split — 가장 중요한 원칙

**공식 test 83케이스는 어떤 fold의 train에도, val에도 절대 들어가면 안 된다.**
최종 성적은 test로만 낸다. 공식 val 42는 fold1~4에서 학습에 써도 된다(데이터가 늘어 이득).

| split | 케이스 | 규칙 |
|---|---|---|
| train | 292 | 자유롭게 학습 사용 |
| val | 42 | fold0의 검증셋. fold1~4에서는 학습에 포함해도 됨 |
| **test** | **83** | **어떤 fold에도 등장 금지 (held-out)** |

출처: `dataset/TopAneu/dataset_split.json` (환자단위 grouping 포함)

### val 을 학습에 넣지 않는다 — 2026-08-18 사용자 지시

**별도 지시가 없으면 train / val / test 구분을 그대로 지킨다.**
학습은 train 292 로만, 하이퍼파라미터 선택은 val 42 로, 최종 성적은 test 83 으로 낸다.

- nnU-Net fold1~4 가 val 을 학습에 포함하는 것은 위 표에 적힌 대로 허용이지만,
  **분류기(C 계열) 학습셋에 val 병변을 넣는 것은 기본적으로 하지 않는다.**
- 실제로 C32 에서 val 43병변을 넣어 test cov.MCC 0.3306 -> 0.3563 이 나왔으나
  (2026-08-18) 사용자 지시로 철회했다. val 이 학습에 들어가면 **선택에 쓸 정직한
  셋이 없어져** 이후 모든 하이퍼파라미터를 test 로 고르게 되는 것이 이유다.
- 다시 넣으려면 명시적 지시가 있어야 한다.


### splits_final.json은 반드시 이 스크립트로 만든다
```bash
export nnUNet_preprocessed=$TOPANEU_ROOT/nnunet/nnUNet_preprocessed
export TOPANEU_DATA=$TOPANEU_ROOT/dataset/TopAneu
python rebuild_417/make_splits_417.py <dataset_id> [<dataset_id> ...]
```
- fold 0 = 공식 split 그대로 (train 292 / val 42) — 모든 실험의 기준
- fold 1~4 = train∪val을 환자단위로 4등분해 val로 사용
- test 83은 전 fold에서 제외 (스크립트가 assert로 강제)

> ⚠️ **nnU-Net이 자동 생성한 splits_final.json을 그대로 쓰면 안 된다.**
> 기본 동작은 전체 케이스를 무작위 5-fold로 나누므로 test가 train에 섞인다.
> 실제로 Dataset720이 이 상태였고(test 83 중 59개 유출), 그 split으로 학습된 실험들은
> `*_TESTLEAK` 접미사를 붙여 격리해 두었다 — **공식 평가에 사용 금지**.

## 2. 실험 명명 규칙

| 접두 | 대상 |
|---|---|
| **A** | 동맥류 검출 (aneurysm detection) |
| **V** | 혈관 분할 (vessel segmentation, 36클래스) |
| **C** | 클래스·위치 지정 (location classification, 52클래스) |

- **정수 증가** (A1 → A2) = 새로운 개념 도입: 입력 데이터 교체, 아키텍처 교체, 새 기법 추가
  번호는 **실제로 실험을 돌린 타임라인 순서**로 부여한다
- **`-N` 접미사** (A1-2) = 같은 개념 안에서 파라미터만 조정 (loss 종류, weight 값, epoch 수)
- **`-fN` 접미사** (A1-f1) = fold만 다름
- **`_TESTLEAK` 접미사** = 공식 split 위반으로 무효 처리된 실험

폴더명 예: `A5-2_resencl_plainz_topk_417_f0`

## 6. 평가 시 주의

### 6-0. 보고·판정 기준 = **공식 개정 eval** — 2026-09-16 사용자 지시 (6-1 을 대체)

**앞으로 모든 보고·비교·판정은 조직위 개정 eval(`experiments/D1_newdata/neweval2.py` 의 `new` 블록, commit 60765a5)로 한다.**
covered_gt(`adjusted_div_present`) 기준은 더 이상 대표값으로 쓰지 않는다. 옛 기록을 인용할 때만 그 출처를 밝히고 병기한다.
- 7지표 전부 적는다: PRECISION · RECALL · F1 · MCC · DICE · VOLSIM · HD95(낮을수록 좋음).
- 공식 순위는 지표별 순위의 평균이므로 **MCC 하나로 기각·채택을 결정하지 않는다**(K1 재검토 2026-09-16).
- 시드 산포를 함께 적는다(시드 0~4 또는 0~9 평균 ± 표준편차, 개선 시드 수).

### 6-1. (구) 외부 기록은 covered_gt 기준 — 2026-08-17 (2026-09-16 6-0 으로 대체됨)

**성능 숫자를 밖으로 적을 때 대표값은 `covered_gt` 분모 값이다.**

- `covered_gt` = eval JSON의 **`adjusted_div_present`** — 그 split의 **GT에 등장하는 클래스 수로 나눈** 평균.
  조직위 `evaluate.py`의 `evaluation_average`는 항상 52로 나눈다(= `official_div52`).
- split별 분모: **test 83 → 36클래스** / **val 42 → 33클래스**
  (데이터셋 전체 non-empty는 43클래스. 전역 0건 9개 = 3, 9, 10, 12, 13, 14, 18, 20, 52)
- **`official_div52`도 함께 적는다** — 리더보드가 ÷52이므로 비교 가능성이 필요하다.
- **6지표 전부** 기록: Precision · Recall · MCC · Dice · VolSim · **HD95(낮을수록 좋음)**
- **대표지표·모델 선택 기준은 MCC** (2026-08-17 사용자 지시). 표 정렬과 "최고" 판정은 MCC로 한다.
  6지표는 전부 적되 순위는 MCC로 매긴다.
- 복합 `(P + R + MCC + Dice + VolSim + (1 − HD95)) / 6` (**aligned**)은 **참고값으로만** 함께 적는다.
  HD95 원값을 그냥 평균하는 literal 정의는 나쁜 값이 점수를 올리므로 쓰지 않는다.
  ⚠️ MCC 기준과 복합 기준이 갈리는 사례가 실재한다(C27 th0.15: MCC는 열세, 복합은 우세).
  **갈릴 때는 MCC를 따르고, 갈렸다는 사실 자체를 기록에 남긴다.**

**혼동 금지 — "covered"가 두 가지다**

| 용어 | 정체 |
|---|---|
| `covered_gt` **분모** (`adjusted_div_present`) | 평균 분모를 52 → GT 등장 클래스 수로 교체. ← **기록 기준은 이것** |
| `--covered-gt` **평가모드** (`eval_mode: covered_gt`) | 검출기가 덮은 GT 병변만 남겨 **GT 마스크로** 채점. 분류기 단독 측정용. 이 모드에서는 예측=GT라 TP의 Dice=VolSim=1, HD95=0 → **Dice와 VolSim이 항상 같은 값이 되고 경계 품질을 전혀 재지 않는다.** 리더보드 예측용으로 쓰면 안 된다 |

**분모를 바꿔도 P·R·MCC·Dice·VolSim은 정확히 52/36배 스케일이라 순위가 안 바뀐다. HD95만 비례하지 않는다** —
GT에 없는 클래스에 예측을 내면 각각 정확히 1.0을 기여하기 때문(`hd_fn`은 한쪽 마스크가 비면 1 반환).
그래서 **복합 순위가 분모에 따라 뒤집힐 수 있다**(÷52는 확률평균 1위, ÷36은 vote2 1위였다).
**HD95는 같은 분모 안에서만 비교한다.**

### 6-1b. 재현성 — 시드 산포보다 작은 차이는 근거가 아니다 — 2026-08-19

**측정(2026-08-19, E4).** 같은 설정에서 분류기 `random_state` 만 0~4 로 바꿔 test 를 5번 돌렸다.

| 설정 | 시드0 | 시드1 | 시드2 | 시드3 | 시드4 | 평균 ± 산포 |
|---|---|---|---|---|---|---|
| rf β0.5 τ0.5 | 0.3306 | 0.3631 | 0.3331 | 0.3793 | 0.3323 | **0.3477 ± 0.0199** |
| et β0.5 τ0.5 | 0.3609 | 0.3022 | 0.2813 | 0.3330 | 0.3109 | **0.3177 ± 0.0273** |

(test cov.MCC) 시드만으로 폭이 **0.0487** 이다. 우리가 채택 근거로 삼았던 개선폭
(C26 +0.0045 · C31 +0.0073 · C36 +0.0303)이 전부 이 폭 안에 들어간다.
C36 은 **부호까지 뒤집혔다** — 보고 +0.0303, 시드평균 −0.0300, ET 가 이긴 시드 1/5.
하필 `random_state=0` 이 ET 의 유일한 승리였다.

원인은 지표 구조다. test 는 병변 87 / 분모클래스 36 이라 **희소 클래스 병변 1개가
cov.MCC 를 0.0278 움직인다.** 즉 우리는 병변 1~2개짜리 차이로 실험을 채택해 왔다.

**규칙**

1. **test 성능을 보고할 때 시드0 값과 시드평균±산포를 병기한다.**
   시드0 은 팀원 단발 숫자와 1:1 비교용, 시드평균은 실제 값이다.
   ```
   rf β0.5 τ0.5   cov.MCC 0.3306 (시드0, 팀 비교용)
                           0.3477 ± 0.0199 (시드 5판)
   ```
   시드는 `CLF_SEED` 환경변수로 준다 (`c5_location_v2.py` `_seed()`).
2. **시드 산포보다 작은 차이는 채택 근거로 쓰지 않는다.** "우연히 좋은 시드"와 구분 불가다.
3. **케이스별 원자료를 남긴다.** `c5_location_v2.py` 는 `c5_percase_{split}_{tag}.json` 을
   자동 저장한다. 이게 있어야 사후에 부트스트랩 신뢰구간을 낼 수 있다
   (`e6_bootstrap.py`). 집계값만 저장하면 오차범위를 영영 못 낸다.
4. 차이가 애매하면 **병변 단위로 세어본다** (`e2_model_diff.py`).
   "몇 개에서 갈렸고 누가 몇 승인가"가 지표 델타보다 정직하다.
   C36 은 test 3승3패·val 1승1패로 **정답 개수가 같았다** — 차이는 전부 클래스 운이었다.

### 6-1c. 내부 판정 숫자를 팀 표에 올리지 않는다 — 2026-08-19 사용자 지시

팀은 **동일 split · 조직위 `evaluate.py` · covered_gt** 로 점수를 내서 서로 비교한다.
그 비교 가능성을 깨면 안 된다.

| 숫자 | split | 분모 | 팀표·노션 |
|---|---|---|---|
| test 83 e2e | 공식 test | present 36 | **올린다** |
| 292 OOF e2e (E1b) | 학습코호트 | present **43** | ❌ |
| 268병변 CV (E3·E5) | 학습코호트 | 43 | ❌ |

**292 OOF 와 CV 숫자는 절대값이 test 와 비교 불가다** — 분모 클래스 수부터 다르다(43 vs 36).
용도는 **순위 하나뿐**이다: 어느 설정이 나은지 고르고, **고른 설정의 test 83 점수를 보고한다.**
val 42 로 고르고 test 로 보고하던 구조와 같고, 고르는 자만 42 → 292 로 바꾼 것이다
(val 42 로 고르는 것이 실패한 사례: C39 val +0.006 → test −0.074, C36 val 우세 → 시드평균 열세).

### 6-2. 일반 주의

- **crop 데이터셋의 내부 validation ≠ 전체볼륨 성능.**
  Dataset740(lesionscale)은 병변 중심 crop window에서 검증하므로 전체영상에서 잰
  Dice와 같은 잣대가 아니다. 비교하려면 원본 전체볼륨으로 sliding-window 추론 후 평가.
- **초소형 병변에서 voxel Dice는 검출능력을 과소평가**한다.
  병변 단위 sensitivity와 케이스당 위양성 수를 함께 보고한다.
- 혈관 후처리(close→prune→adj→endpoint)는 Dice를 거의 안 바꾸면서
  조각 수를 60% 줄인다. 파편화 지표를 함께 기록할 것.
- 클래스별 Dice가 0인 "죽은 클래스"는 원인이 두 가지다 —
  (a) 데이터 부족 (b) 학습 중 붕괴 후 미회복. 학습로그의 per-class 추이를 보고 구분한다.
  (b)라면 CE class weight로 구제 가능(V4/V4-2 사례).
